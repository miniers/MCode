# 发送后消息可见性修复方案

**目标：** 空闲发送后新消息进入可视区；开启发送后置顶时停在时间线顶部。运行中发送后，对应排队条目进入队列可视区。

**范围：** 只设计修改 `web/src/components/ThreadView.tsx`、`web/src/components/ThreadTimeline.tsx`、`web/src/components/thread/useSendAnchor.ts` 和 `web/src/components/thread/QueuedFollowUpSection.tsx`；按需增加相关测试。不更改协议或主动收起键盘。以下为静态分析，尚未运行或实机验证。

### 4. 移动端键盘和高度变化

### 5. 按可能性排序的根因

1. 运行中：队列有独立限高滚动容器，发送后没有定位具体新条目；队列较长时可直接复现。
2. 空闲且贴底已暂停：新消息不在虚拟渲染范围，锚定只等待 DOM，30 次后直接放弃并跳到底。是否是当前反馈的主要场景尚待复现。
3. 高度变化与快速长回复：padding 固定且满屏会主动释放，可能打断置顶。静态代码支持此机制，未验证发生频率。
4. 非 accepted 的不确定结果提前解除：机制确定，但 pending 作为正常发送返回值并非常规成功路径，不能把它当作已证实的普遍主因。
5. ID 替换依靠最新用户消息推断：存在身份和过渡状态风险，但本路径没有证据证明一定发生乐观替换。

## 实施步骤

1. **使虚拟目标行可挂载并精确定位。** 以 `web/src/components/ThreadTimeline.tsx:2891` `      virtualizer.scrollToIndex(index, { align: 'start' });` 为现有实现锚点，为发送锚定提供独立的消息 ID 请求/回调；在 `VirtualTimeline` 中通过 `web/src/components/ThreadTimeline.tsx:164` `  if (item.type === 'message') return item.message.id === messageID;` 所属 `timelineItemContainsMessage` 找目标 index，先 `scrollToIndex(index, { align: 'start' })`，随后由 `useSendAnchor` 的现有 pump 以已挂载节点做精确顶对齐。通过 `ThreadView` 传递请求，避免复用会触发提问导航高亮的请求。只在找不到节点且目标 index 存在时发一次请求，等待虚拟行挂载；消息暂未进入 items 时在 items 更新后重试，避免每帧重复调用 `scrollToIndex`。对非虚拟分支继续使用现有 DOM 校正。对实在不存在的行保留有界等待，失败时至少滚到底并在可见消息到达后重新定位，不能静默永久失效。验证：用户上滑远离底部、发送后目标原本位于 overscan 外；检查新消息挂载且顶部与滚动区顶部误差不超过 2px；覆盖空会话和普通已挂载行。
2. **让锚定跨结果不确定与视口变化。** 以 `web/src/components/ThreadView.tsx:1933` `      if (params.whenRunning !== 'queue') releaseSendAnchor(true);` 为锚点，只对确定失败/同步抛错解除；pending、submitting、unknown 保留同一次发送的等待状态，并关联 action ID 监听后续结算：accepted 后继续等消息，failed 后 `release(false)`；切换会话、用户主动滚动、开启新发送时清理，避免旧请求锚到未来无关消息。优先用 accepted 的 `messageID` 匹配权威消息；仅在确实没有服务端 ID 时沿用基线回退，替换时核对发送动作身份而非无条件认定最新消息相同。以 `web/src/components/thread/useSendAnchor.ts:269` `      const padding = container ? container.clientHeight : 0;` 为锚点，在 holding 期间用 `ResizeObserver` 更新 padding 并触发 pump；等 React 提交 padding 后再校正，不将 resize 当作用户手势。为满足本任务的持续置顶目标，取消以回复超过一屏为由的自动释放：`web/src/components/thread/useSendAnchor.ts:214` `      if (anchorShouldRelease(replyHeight, container.clientHeight)) {`；保留用户手势、跳到最新、切会话及开关关闭时释放。验证：accepted、failed、unknown 后结算、断线换 client、临时 ID 替换以及旧新 ID 短暂并存；键盘保持打开时改变视口高度，验证置顶与 padding；长回复不自动跳底，手动滚动仍可解除。开关关闭时验证恢复贴底和发送后消息可见。
3. **定位实际排队条目。** 以 `web/src/context/remoteThreadActions.ts:243` `          followUpID: result.followUpID,` 为锚点，在 `ThreadView` 发送 accepted 且 `action.queued` 时，将本次 `followUpID` 和递增请求序号交给 `QueuedFollowUpSection`；以 `web/src/components/thread/QueuedFollowUpSection.tsx:339` `                    <div key={followUp.id} className="flex items-center gap-2">` 为锚点绑定条目节点，待队列快照包含该 ID 且 DOM 已提交后，仅调整队列 section 的 `scrollTop` 使目标条目可见，避免 `scrollIntoView` 改动时间线或页面。处理快照先于或晚于 RPC、重复发送、切换会话与用户主动滚动；没有 `followUpID` 时只在能通过本次发送前后快照可靠识别唯一新条目时定位，否则保留请求并等待可确认身份，不猜最后一项。验证：队列超过 30dvh、处于顶部与底部、重复正文及分组，确认本次条目可见且时间线不跳动；测试快照与 RPC 两种到达顺序，以及无 ID/队列不可用场景。检查子代理会话是否可排队，若可则补上等价展示与定位。
4. **回归验证。** 为上述关键分支编写有行为意义的组件测试：虚拟行起初不挂载、请求后挂载并对齐；队列按 followUpID 滚动；不确定结果不会丢锚，失败不强制跳底；resize 更新 padding、长回复保持锚定、手动滚动解除。随后在手机浏览器及桌面窄屏实测开关开/关、空闲/运行中、软键盘开启、长列表和长回复。此文档编写阶段按要求未运行构建、测试、lint 或类型检查。
